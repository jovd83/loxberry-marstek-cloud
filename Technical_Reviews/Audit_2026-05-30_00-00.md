## Executive Summary
- **Maintainability Score: 82 / 100**
- **State of the Union:** The plugin is a compact, well-structured LoxBerry bridge with solid security guardrails (0600 config, URL allow-list, credential redaction in logs, CSRF mitigation). The Python daemon and Perl CGI follow clean separation of concerns. The most significant gap is boot-time MQTT resilience — the daemon crashes if the broker is unavailable at startup, requiring a manual restart. Version strings have drifted in two locations and the CI/validation pipeline is absent. Everything else is polish and ergonomics.
- **Top Risks:**
  1. MQTT broker unavailable at boot crashes the daemon permanently (no retry on `connect()`).
  2. Version string in `index.cgi` is `0.1.2`; plugin is `1.0.0` — users see the wrong version in the UI header.
  3. No CI pipeline (no `validate.yml`); packaging and correctness rely entirely on manual discipline.

## Architecture Snapshot
- **Entry Points:** `daemon/daemon` (bash, invoked by `loxberry.service` at boot and by CGI on save); `bin/marstek-cloud.py` (Python daemon process); `webfrontend/htmlauth/index.cgi` (Perl CGI, browser-facing settings UI)
- **Core Layers:**
  - *Infrastructure:* `daemon/daemon` — privilege drop, pidfile, SIGTERM/SIGKILL lifecycle
  - *Application / polling:* `MarstekCloudClient` (API auth + device poll), `MqttPublisher` (MQTT bridge), `poll_once` orchestrator
  - *Configuration:* `config/default.json` (on-disk store), `sanitize_config` + `load_config` (Python), Perl CGI POST handler (writes via `LoxBerry::JSON`)
  - *Presentation:* `templates/settings.html` (HTML::Template), `index.cgi` (CGI renderer)
  - *Build:* `build_zip.py` (packaging script, not shipped in the ZIP)
- **Hot Files / Hot Paths:**
  - `bin/marstek-cloud.py` — all runtime logic; most sensitive code
  - `webfrontend/htmlauth/index.cgi` — config mutation and daemon restart trigger
  - `daemon/daemon` — privilege boundary (root → loxberry user)
- **Constraints / Unknowns:**
  - No automated test suite; all validation is manual or via Docker sandbox
  - Perl modules (`LoxBerry::IO`, `LoxBerry::JSON`, `LoxBerry::Web`) unavailable for static analysis on Windows
  - Marstek Cloud API response shapes inferred from field names; not documented by vendor

## Findings Table

| :--- | :--- | :--- | :--- | :--- |
| `bin/marstek-cloud.py:398–419` (`MqttPublisher.__init__`) | **High** | MQTT connect not retried on failure | If the MQTT broker is not yet ready at daemon boot (common boot-time race), `self.client.connect()` raises `ConnectionRefusedError` and the daemon crashes with no recovery. The user must manually restart. `paho`'s background `loop_start()` reconnect only fires after a successful initial `connect()`. | Wrap the initial `connect()` in a retry loop with backoff (e.g., 3 attempts, 5 s apart) before `loop_start()`. Log a warning on each failure and raise only after all retries exhausted. Mirror the pattern already used in `_with_retry()`. |
| `webfrontend/htmlauth/index.cgi:13` | **Medium** | Version string hardcoded and stale | `my $version = "0.1.2"` is shown in the UI header as `v0.1.2` while `plugin.cfg` and `README.md` both say `1.0.0`. Users and support conversations reference the wrong version. | Parse `plugin.cfg` at CGI startup using `LoxBerry::System` or a `qx(grep '^VERSION=' ...)` one-liner, or maintain a single shared version constant. The simplest fix: update the hardcoded string to `1.0.0` now, then document that it must be bumped together with `plugin.cfg` on every release. |
| `bin/marstek-cloud.py:322` (`_request`) | **Medium** | User-Agent version string stale | `User-Agent: LoxBerry-marstek-cloud/0.1` — `0.1` predates the plugin's first published release (`v0.1.0`). Serves as a diagnostic fingerprint in Marstek server logs; stale value hampers future vendor debugging. | Source the version from a single module-level constant (`PLUGIN_VERSION = "1.0.0"`) and use it in the User-Agent and wherever else version identity appears. |
| `webfrontend/htmlauth/index.cgi:95` | **Medium** | `system()` call uses string interpolation | `system("$daemon restart >>'$lbplogdir/daemon-restart.log' 2>&1")` — shell string interpolation is used rather than list form. If `$lbplogdir` contains a space the redirect path breaks silently. `$daemon` and `$lbplogdir` are LoxBerry system variables (not user-controlled) so actual injection risk is low, but the code is fragile. | Use Perl's list form for the process part and handle redirection explicitly: redirect STDOUT/STDERR before forking, or pass the log path as a shell-quoting-safe single-quoted argument. At minimum, add `quotemeta`/`Shell::quote` around the log path. |
| `.github/workflows/` (absent) | **Medium** | No CI/CD pipeline | The repo has no `validate.yml` or equivalent. The LoxBerry plugin template standard (referenced in the project README) calls for a `validate.yml` CI step. Without it, packaging correctness and permission flags are validated only manually, and version drift (see findings above) goes undetected. | Add a minimal GitHub Actions workflow that runs `python build_zip.py` and verifies the ZIP is produced, plus `python -m py_compile bin/marstek-cloud.py`. This matches the `jovd83/LoxBerry-Plugin-mammotion-mower` template baseline. |
| `bin/marstek-cloud.py:60–70`, `config/default.json:19–29`; no corresponding UI controls | **Medium** | Advanced config params not reachable from the UI | `data_points`, `ignored_device_types`, `request_timeout_seconds`, and `request_attempts` are all meaningful operational controls (filtering out devices, tuning retry aggressiveness) but are invisible in the settings page. Users must SSH and hand-edit JSON, which is fragile and undiscoverable. | At minimum add read-only display of these values in the Advanced panel with a note that they are JSON-only. Optionally add a collapsed "Expert" section with editable fields for `request_timeout_seconds` and `request_attempts` (bounded number inputs already used elsewhere in the form). |
| `bin/marstek-cloud.py:82`; `handle_shutdown` | **Low** | Module-level mutable `RUNNING` flag | `RUNNING = True` at module scope, mutated from a signal handler. Works correctly for a single-threaded daemon but is a shared-mutable-state smell; harder to unit-test and reason about. | Replace with a `threading.Event` (`_shutdown = threading.Event()`). Signal handler calls `_shutdown.set()`; the sleep loop becomes `_shutdown.wait(timeout=1)` which is both idiomatic and directly testable. |
| `templates/settings.html:222–233` | **Low** | `<script>` placed mid-`<form>` between panels | The `<script>` block that hides/shows manual broker fields is placed between two `<div class="panel">` siblings inside the `<form>`. Valid HTML5, but structurally unusual — parsers and linters may flag it, and future template authors may move panels without realising the script depends on element ordering. | Move the `<script>` block to just before `</form>` (or to a `<script>` section at the end of the template file). No functional change, improves structural clarity. |
| `build_zip.py:46` | **Low** | Unexplained legacy exclusion pattern | `r"^jovd83-.*\.zip$"` excludes a `jovd83-*.zip` naming pattern that no longer matches the current `marstek-cloud-*.zip` artifact naming. Purpose is not documented. | Remove the pattern if it no longer serves a purpose, or add a comment explaining its origin (e.g., protecting against accidentally packaging a renamed artifact from a prior naming convention). |

## Refactor Sequence

1. **Fix MQTT boot-time crash** (`bin/marstek-cloud.py` — `MqttPublisher.__init__`) — highest operational impact, protects clean first-boot experience.
2. **Fix version string drift** (`index.cgi:13` to `1.0.0`; `marstek-cloud.py:322` User-Agent constant) — low-risk one-liner fixes, eliminates user-visible confusion.
3. **Harden `system()` call in CGI** (`index.cgi:95`) — replace string-interpolated shell call with a safer form.
4. **Add GitHub Actions CI** (`.github/workflows/validate.yml`) — packaging + syntax check baseline.
5. **Replace `RUNNING` flag with `threading.Event`** (`marstek-cloud.py`) — small refactor, improves testability.
6. **Move `<script>` in template** (`settings.html:222`) — cosmetic, no logic change.
7. **Clean up legacy exclusion in `build_zip.py`** — remove or document `jovd83-.*\.zip` pattern.
8. *(Optional)* **Expose advanced config params in UI** — scope to be confirmed; lowest urgency.

## Open Questions Or Blockers

- **`data_points` / `ignored_device_types` UI controls (item 5):** Adding these would require new form fields, Perl save logic, and HTML template changes across three files. Recommend scoping this as a separate story unless the user confirms they want it included in this refactor.
- **Perl static analysis:** `perl -c` requires LoxBerry modules unavailable on the Windows dev machine. The CGI was audited by manual inspection only. Recommend running `perl -c index.cgi` on a LoxBerry Docker instance before shipping the refactored CGI.
- **Marstek API shape validation:** `get_devices()` trusts the `"data"` list from the API with no schema check. This is deliberately loose (vendor API not documented), but a future finding worth revisiting if the API changes.
